# Shared Flutter desktop and mobile app plan

**Date:** 2026-09-20  
**Status:** implementation plan and execution record  
**Scope:** one Flutter application in this repository, built for Windows, Linux, Android, macOS, and iOS from the same Dart code.

## 1. Source-of-truth decision

The existing React application remains the browser client and the Cloudflare Worker remains the API/data source. The native client will live under `apps/timetracker/` in this repository:

```text
apps/timetracker/
├── lib/                 # one shared Dart UI and API client
├── test/                # shared Dart tests
├── android/             # generated platform runner/config
├── ios/                 # generated platform runner/config
├── linux/               # generated platform runner/config
├── macos/               # generated platform runner/config
└── windows/             # generated platform runner/config
```

There will be no separate mobile and desktop Dart apps. Platform folders contain only runner/configuration code generated by Flutter; product behavior stays in `lib/`.

## 2. Feature matrix

### Phase A - implemented in this pass

| Capability | Mobile | Desktop | API/source |
|---|---:|---:|---|
| API base via `--dart-define` | ✓ | ✓ | Worker REST |
| Bootstrap active timer, entries, master data | ✓ | ✓ | `GET /api/bootstrap` |
| Always-visible active timer/status | ✓ | ✓ | timer start/stop |
| Start timer with client/project/activity, note, tags | ✓ | ✓ | `POST /api/timer/start` |
| Stop timer and elapsed display | ✓ | ✓ | `POST /api/timer/stop` |
| Recent time-entry list with duration/cost | ✓ | ✓ | bootstrap entries |
| Dark/light/system theme | ✓ | ✓ | local device preference |
| Responsive navigation | bottom navigation on narrow screens | side navigation on wide screens | shared layout |
| Loading, empty, API error, retry, and action feedback | ✓ | ✓ | shared widgets |
| Settings workspace summary and API connection check | ✓ | ✓ | bootstrap |

### Phase B - next native parity slice

- Edit closed entries using `PATCH /api/entries/:id`.
- Client/project/activity management, archive/restore, rates, currencies, emoji, and image paste/upload.
- Dashboard totals and breakdowns from `GET /api/dashboard`.
- CSV export and native share/save flow.
- Voice-to-draft capture using a platform-compatible recorder package; Gemini remains server-side.

### Phase C - platform capabilities

- Local notifications for unusually long timers.
- Secure token storage when authentication is introduced.
- Offline draft queue with idempotent writes.
- Deep links to `/clients/:id`, `/projects/:id`, and `/activities/:id`.

## 3. Cross-platform constraints

- Use Flutter Material widgets and Dart libraries that work on all five requested platforms.
- Keep `dart:io` out of shared UI code; HTTP uses the `http` package.
- Do not add platform-specific business logic to `lib/`.
- API endpoint is injected at build/run time:
  - desktop local: `http://127.0.0.1:8787`
  - Android emulator local: `http://10.0.2.2:8787`
  - physical device: the development machine's LAN address
  - production: deployed Worker URL
- macOS/iOS require normal Apple signing, bundle identifiers, and Xcode toolchains; no product-code fork is needed.
- Windows and Linux require their normal Flutter desktop toolchains; the same Dart build is reused.

## 4. Build commands

From `apps/timetracker`:

```bash
flutter pub get
flutter run -d windows --dart-define=API_BASE_URL=http://127.0.0.1:8787
flutter run -d linux --dart-define=API_BASE_URL=http://127.0.0.1:8787
flutter run -d android --dart-define=API_BASE_URL=http://10.0.2.2:8787
flutter build windows --dart-define=API_BASE_URL=https://api.example.com
flutter build linux --dart-define=API_BASE_URL=https://api.example.com
flutter build apk --dart-define=API_BASE_URL=https://api.example.com
flutter build macos --dart-define=API_BASE_URL=https://api.example.com
flutter build ios --dart-define=API_BASE_URL=https://api.example.com
```

Only the target/build command and API define change. The Dart source does not.

## 5. UX rules carried from the web app

- The timer is the primary action and remains visible while navigating.
- The first-run state explains the setup order: client → project → activity.
- Primary actions use labels, not icon-only controls.
- Success and error messages explain what happened and what to do next.
- The desktop layout uses available width without making the mobile layout a squeezed desktop table.
- Touch targets are at least comfortable Material button sizes; keyboard focus remains available on desktop.

## 6. Acceptance criteria

- A single Flutter project builds the shared app for the requested platform targets.
- The app can load the current Worker bootstrap endpoint, start and stop a timer, and render recent entries.
- A running timer remains visible after route/tab changes.
- API failures offer retry and do not leave an indefinite spinner.
- Theme choice is local and does not affect server data.
- `flutter analyze` and shared tests pass.
- Platform-specific signing/toolchain requirements are documented rather than hidden in Dart code.

## 7. Execution record

The implementation began with the Phase A shared client and generated platform runners. Phase B and C remain intentionally separate so the first native build is small, useful, and easy to verify on every target.

## 8. What was implemented

Created `apps/timetracker/` as one Flutter project with generated runners for Windows, Linux, Android, macOS, and iOS. All product code is shared in `lib/main.dart`; no platform-specific business logic was added.

Implemented Phase A:

- bootstrap loading from the existing Worker API;
- active timer badge and start/stop flow;
- client, project, activity, note, and tags selection;
- recent entries list;
- dashboard starter view;
- settings theme choices and API connection refresh;
- desktop `NavigationRail` and narrow-screen `NavigationBar`/drawer;
- loading, empty setup, empty entries, error, retry, and action acknowledgement states;
- API base configuration through `--dart-define=API_BASE_URL=...`.

The generated platform folders are intentionally retained so the same Dart app can later be signed and packaged for macOS/iOS without a source fork.

## 9. Verification results

```bash
flutter test
flutter build apk --debug
```

The Android debug APK built successfully. Flutter analysis and the shared widget smoke test pass.

Linux compilation was attempted and is blocked only by the local machine missing CMake:

```text

```

Windows, macOS, and iOS builds require their respective host toolchains: Visual Studio on Windows, Xcode/signing on macOS/iOS, and CMake/GTK development packages on Linux. Those prerequisites do not require changes to the shared Dart code.

The architecture remains one codebase: changing only the Flutter target/build command and API define selects the platform.
